# 기능 이식 기록 (1차 프로토타입 통합)

1차 프로토타입을 기준으로 기능을 하나씩 이식·추가한 기록입니다.
작업 브랜치는 `feature/integrate`이며, 단계마다 기준 job과 비교해 확인한 뒤 커밋했습니다.

## 진행 방식

- 기준 job 2개(base-a, base-b)를 먼저 만들어 두고, 각 단계 후 같은 job(또는 복사본)으로 결과를 비교했다.
- 기존 파이프라인 구조(단계 분리, 결과 파일 재사용, `--from-step`·`--scene` 부분 재생성)는 유지하고, 기능 단위로만 끼워 넣었다.
- API 키(`.env`)와 실행 결과(`jobs/`)는 커밋하지 않는다.

## 1. API 비용 집계

**내용**
- 단계별 토큰·이미지·글자 사용량을 단가표로 환산해 `log.json`의 `cost`에 누적 기록한다 (재실행분 포함).
- 단가: gpt-5.4-mini 입력 $0.75 / 출력 $4.50, gpt-image-2 텍스트 입력 $5 / 이미지 출력 $30 (1M 토큰당).
- 이미지 단계가 실제 이미지 토큰 사용량을 기록하도록 변경했다.
- TTS 단가는 `.env`의 `ELEVENLABS_USD_PER_1K_CHARS`로 넣으며, 값이 없으면 "단가 미확인"으로 표시한다.
- 실행이 끝나면 로그에 `API 비용(누적): $…`을 출력한다.

**확인**
- 기준 job 재실행으로 비용이 기록되는지 확인했다. 이미지 1장(medium)은 약 $0.042, 영상 1건은 TTS를 빼고 약 $0.28이다.

## 2. 대본 수치·조건 검증

**내용**
- 대본을 만든 뒤 자막 문장(숫자가 원래 표기로 남아 있는 문장)을 원문과 대조해, 수치·날짜·회차·조건 오류를 찾는다.
- 오류가 있으면 대본을 한 번 다시 작성한다. 다시 쓴 결과가 기존 대본 규칙(길이·포인트 등)을 더 어기지 않을 때만 교체한다.
- 그래도 남은 오류는 멈추지 않고 경고와 함께 `log.json`의 `fact_issues`에 남긴다.
- 기본 추론 강도로는 회차·날짜 짝 오류를 놓쳐서, 검증 호출만 `reasoning_effort=low`로 실행한다 (1회 약 $0.003).
- `.env`: `FACT_CHECK=1`(끄려면 0), `FACT_CHECK_EFFORT=low`

**확인**
- 원문과 다른 회차를 일부러 넣은 대본에서 오류를 찾아 수정하는 것을 확인했다.

## 3. 그림 속 글자 차단 + 이미지 흑백 후처리

**내용**
- 대본 검사 규칙에 "그림 설명(image_prompt)에 글자를 부르는 표현 금지"를 추가했다. 숫자, 따옴표 문구, 한글, 그리고 `prompts/image_text_words.txt`의 단어(label, sign, text, written 등)가 있으면 대본을 다시 요청한다.
- 단어 목록은 코드 수정 없이 텍스트 파일에서 추가·삭제할 수 있다 (`#` 주석 가능).
- 생성된 이미지를 흑백으로 바꾸고, 거의 흰색인 픽셀을 순백으로 정리하는 후처리를 추가했다.
- `.env`: `IMAGE_GRAYSCALE=1`, `IMAGE_WHITE_THRESHOLD=235`

**함께 수정한 버그**
- 드로잉 순서 계획의 영역 좌표가 1000을 넘으면 드로잉이 실패하던 문제를 고쳤다 (`steps/s06_animate.py`의 `_clamp_box`).

**확인**
- 글자 표현이 들어간 그림 설명이 검사에 걸리는 것을 확인했다.
- 현재 이미지는 이미 흑백에 가까워서 영상에서 차이가 거의 없다. 후처리는 화풍이 흔들릴 때를 대비한 안전장치로 둔다.

## 4. 글자 단위 자막 싱크

**내용**
- TTS를 `/with-timestamps` 엔드포인트로 바꿔, 음성과 함께 글자별 발화 시각을 받는다.
- 무음 정리로 앞부분을 잘라 낸 만큼 시각을 보정해 `scenes.json`에 `speech_text`, `char_times`로 저장한다.
- 자막 문장(CBT, 60점)과 TTS 문장(씨비티, 육십점)은 글자가 달라서, 쉼표·마침표 뒤의 구간 시작점끼리 짝을 지어 시각을 맞추고 구간 안은 글자 위치 비율로 나눈다.
- 시각 정보가 없는 예전 job은 기존 방식(글자 수 비율)으로 처리한다.

**확인**
- 예시 문장에서 두 번째 자막이 실제 발화 시작(2.69초)에 정확히 넘어갔다. 기존 방식은 0.16초 일렀다.
- 기준 job 복사본을 음성부터 다시 만들어 6개 장면 모두 글자별 시각이 기록되는 것을 확인했다.

## 5. 웹에서 장면 수정 후 재생성

**내용**
- 웹 대본 화면의 장면마다 "수정" 버튼을 두고 자막, 읽는 문장, 그림 설명을 고칠 수 있게 했다.
- `POST /jobs/{id}/rerun` API를 추가했다. 바뀐 항목에 필요한 파일만 지우고 같은 대기열로 다시 실행한다.
    - 읽는 문장 → 그 장면의 음성부터
    - 그림 설명 → 그 장면의 그림부터 (음성은 유지)
    - 자막만 → 영상 합성만
- 웹에서 고친 대본은 음성 길이가 30~60초를 벗어나도 다시 쓰지 않고 경고만 남긴다 (`run.py`의 `regen_script`).
- 다시 만든 영상이 브라우저 캐시 때문에 예전 영상으로 보이지 않도록 영상 주소에 수정 시각을 붙였다.

**함께 수정한 버그**
- 실패한 뒤 다시 돌려 성공한 작업이 계속 "실패"로 표시되던 문제를 고쳤다. 완성 영상이 있는지를 오류 기록보다 먼저 확인하고, 진행 단계는 마지막 실행 기록만 보여 준다.

**확인**
- 1번 장면의 읽는 문장을 고치자 그 장면의 음성·드로잉·변환 영상만 다시 만들어졌다. 처리 시간은 65초에서 50초로 줄었고, 새로고침 없이 영상이 바뀌었다.

## 6. 자동 평가 지표 CSV

**내용**
- `python scripts/eval_jobs.py`로 jobs 폴더의 완성 job을 CSV 한 장(`jobs/eval_jobs.csv`)으로 정리한다. API를 호출하지 않아 비용이 없다.
- 지표: 영상·음성 길이, 30~60초 충족, 음성·영상 차이, 핵심 포인트 반영, 대본 형식 위반, 그림 속 글자 장면, 수치 오류, 자막 싱크 장면 수, 자막 최대 오차, 처리 시간, 비용, 실행 횟수
- 형식 위반은 대본 생성 때와 같은 검사 함수로 현재 `scenes.json`을 다시 검사한다 (웹에서 고친 내용 포함).

**확인**
- 기준 job 2개와 테스트 job 1개로 CSV를 만들고, 처리 시간·비용이 `log.json`과 같은 것을 확인했다.

**보류**
- 원문 근거 일치율: 장면마다 근거 문장(`source`) 필드가 있어야 계산할 수 있어서, 대본 담당과 상의 후 추가한다.

## 7. 평가 문서 양식

**내용**

## 설계 메모: 음성 먼저, 그림 나중

파이프라인은 음성(5단계)을 그림(4단계)보다 먼저 실행한다. 이 순서는 의도한 설계이므로 바꾸지 않는다.



### 음성을 먼저 만드는 이유

1. **영상 길이는 실제 음성을 만들어 봐야 정확히 알 수 있다.**
   대본 단계에서는 글자 수로 길이를 예상하지만, 숫자·영문 약어를 한글로 풀어 읽거나(60점 → 육십점, CBT → 씨비티) 문장마다 말하는 속도가 달라서 실제 길이와 차이가 난다. 30~60초 조건은 실제 음성 길이로만 확실하게 판단할 수 있다.

2. **가장 비싼 단계(그림)를 길이 확인 뒤로 미뤄야 비용을 아낄 수 있다.**
   영상 1건 비용(약 $0.28) 중 그림 6장이 약 $0.25로 대부분을 차지한다. 음성은 몇 초면 만들어지고 비용도 적다. 음성을 먼저 만들어 길이가 범위를 벗어나면, 그림을 만들기 전에 대본을 다시 쓰고 음성만 다시 만든다. 순서를 바꾸면 대본이 바뀔 때마다 이미 만든 그림을 버리고 다시 생성해야 한다.

3. **그림과 음성은 서로 기다릴 필요가 없다.**
   둘 다 대본만 있으면 만들 수 있고, 서로의 결과를 쓰지 않는다. 그래서 싸고 빠르며 검증 역할을 하는 음성을 앞에 두어도 잃는 것이 없다.

4. **드로잉 단계에는 둘 다 필요하고, 기준은 음성이다.**
   드로잉 영상(6단계)은 음성 길이에 맞춰 그리는 속도를 정한다. 음성 길이가 먼저 확정되어 있어야 드로잉·자막·렌더가 같은 길이를 기준으로 맞춰진다.

### 단계 번호를 바꾸지 않는 이유

실행 순서는 3 → 5 → 4 → 6이지만 번호는 처음 설계한 그대로 둔다. 번호는 CLI 옵션(`--from-step`), `log.json`의 단계 이름(`s04_image`, `s05_tts`), 코드 파일 이름, 웹 화면의 단계 표시, 팀 문서에서 함께 쓰인다. 번호만 바꾸면 기존 job 기록과 문서가 맞지 않게 되고, 얻는 이점은 없다.

### 알려진 영향

번호와 실행 순서가 달라서, CLI에서 `--from-step 4`(그림부터 다시)를 실행하면 번호상 뒤에 있는 음성(5단계)도 다시 만든다. 영상이 깨지지는 않는다. TTS 비용이 조금 더 들고 장면 길이가 0.몇 초 달라질 수 있을 뿐이다. 그림만 다시 만들려면 웹의 장면 수정 기능을 쓰면 된다. 웹은 장면별로 필요한 파일만 지운다.
